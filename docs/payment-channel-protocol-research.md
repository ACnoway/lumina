# 支付渠道协议与官方接入调研

> 调研日期：2026-10-02
> 适用项目：`ACnoway/lumina`
> 本文记录协议调研、现状判断以及已落地的改造结果；真实商户联调仍需在远程环境完成。

## 1. 结论摘要

当前支付模块仍保留 `PaymentScene` 作为历史订单字段，但它已经不再作为用户请求或 Adapter 下单请求的输入。这个抽象不适合作为外部渠道协议：易支付、支付宝官方和微信支付官方的请求字段、签名算法、下单接口和返回值都不同。

后续应采用以下边界：

1. 用户业务接口只提交金额和用户选择的支付方式，不提交跨渠道通用的 `scene`。
2. 每个渠道 Adapter 自己决定调用哪个官方接口、携带哪些字段、如何签名以及如何解析响应。
3. 统一层只保留订单、幂等、状态、金额校验、回调入账和钱包流水等业务职责。
4. 前端可以继续消费统一的支付动作结果，例如跳转地址、表单、二维码内容或 JSAPI 参数；这些是“结果格式”，不是渠道的“请求格式”。
5. 易支付、支付宝官方、微信支付官方分别使用自己的配置和协议，不在 Adapter 内部互相兼容或伪装成同一套请求格式。

## 2. 当前项目问题

当前实现的主要问题：

- `PaymentScene` 曾同时描述不同渠道的产品形态，导致渠道协议被统一抽象限制；现在只保留为历史兼容字段，用户 DTO 和 Adapter 请求已移除该输入。
- 易支付 `mapi.php` 的 `payurl` 现在优先解析为 `REDIRECT_URL`，不会因为同时返回二维码字段而误判下单失败；没有跳转地址时才解析二维码。
- 易支付配置已增加 `createEndpoint`、`queryEndpoint` 和 `queryMethod`，可明确选择 `mapi.php`/`submit.php` 以及查单方式；查单默认 POST，显式使用 GET 时才会将 key 放入查询串。
- 支付宝和微信 Adapter 已按各自官方产品配置下单；支付宝网关响应必须验签，微信 API v3 的商户请求、响应、回调签名和回调解密均在 Adapter 内处理。

本次改造已按上述边界落地；数据库中的 `PaymentOrder.scene` 暂时保留用于历史订单和旧客户端兼容，新的场景/产品选择由渠道实例配置与 Adapter 决定。

## 3. 易支付协议

### 3.1 协议定位

“易支付”不是一个由单一官方机构维护、所有服务商完全一致的 SDK 标准，而是一组兼容度较高的聚合支付协议。不同服务商可能使用相似的 `pid`、`key`、`out_trade_no`、`notify_url`、`return_url`、`money`、`sign` 字段，但 endpoint、成功返回字段、签名算法和回调扩展字段可能不同。

因此，Lumina 不能只根据 `EPAY` 这个类型推断所有服务商的行为。每个易支付渠道实例至少要绑定一份明确的协议变体和对应服务商文档；真实配置以该商户后台提供的文档为准。

### 3.2 页面跳转支付

多个易支付文档都把页面跳转支付定义为向 `submit.php` 发起 POST 或 GET，请求字段通常包括：

| 字段 | 含义 |
| --- | --- |
| `pid` | 商户 ID |
| `type` | 支付方式，例如 `alipay` 或 `wxpay` |
| `out_trade_no` | Lumina 商户订单号，必须唯一 |
| `notify_url` | 服务器异步通知地址 |
| `return_url` | 用户完成支付后的浏览器跳转地址 |
| `name` | 商品名称 |
| `money` | 人民币金额，通常保留两位小数 |
| `sign` | 按该服务商规则计算的签名 |
| `sign_type` | 常见为 `MD5`，但必须以服务商文档为准 |

成功时通常直接返回或跳转到收银台页面，失败时返回包含错误信息的结果。对于浏览器充值，优先考虑将该页面跳转请求作为易支付 Adapter 的原生支付动作，不再把它转换成支付宝或微信官方的请求模型。

### 3.3 API 接口支付

部分易支付服务商提供 `mapi.php` API 接口。常见请求方式是 POST 表单，金额单位为元，支付方式仍由 `type` 指定。成功响应常见字段包括：

- `code = 1`：请求被渠道接受；
- `trade_no`：易支付侧订单号；
- `payurl`：用户继续支付的跳转地址；
- `msg`：失败原因或提示信息。

`payurl` 是支付动作，不是二维码专属字段。无论上层采用何种浏览器支付方式，只要服务商文档声明该字段为收银台地址，就应按跳转地址处理。

API 方式还可能提供 `api.php?act=order` 查询订单，以及退款接口。查询接口的参数通常包括 `pid`、`key`、`out_trade_no` 或 `trade_no`。由于部分文档示例把商户密钥放在 URL 查询串中，生产环境必须使用 HTTPS，并评估反向代理、访问日志和监控系统记录完整 URL 所造成的密钥暴露风险；能使用 POST 密钥字段时优先使用 POST。

### 3.4 易支付回调

常见异步通知为 GET，字段包括：

- `out_trade_no`：Lumina 订单号；
- `trade_no`：易支付订单号；
- `money`：支付金额；
- `trade_status`：通常只有 `TRADE_SUCCESS` 才表示成功；
- `type`：支付方式；
- `sign`、`sign_type`：通知签名信息。

Lumina 必须先按对应服务商的规则验签，再校验订单号、渠道实例、币种和金额，最后才允许钱包入账。收到合法通知后返回该服务商要求的成功文本，通常为 `success`。

### 3.5 易支付改造方向

后续易支付 Adapter 应按以下方式设计：

1. 不再把 `WEB/H5/QR` 作为易支付请求参数或协议分支。
2. 采用该易支付服务商明确支持的页面跳转接口或 API 接口。
3. `type` 只表达易支付协议要求的支付方式值，例如 `alipay`、`wxpay`。
4. 按 `code`、`msg`、`trade_no`、`payurl` 等易支付字段判断下单结果。
5. 对 `payurl`、HTML 收银台和服务商定义的其他支付动作做明确解析。
6. 对协议变体配置 endpoint、签名算法、回调格式和查询方式，不把一个服务商的扩展字段假设为全部易支付平台的标准。
7. 请求发出后如果结果不确定，不能自动切换到另一个支付渠道，也不能用新的订单号盲目重试。

当前实现状态：上述 1-6 已落地。易支付无效回调签名不会再通过“先查单再入账”的隐式回退路径；需要查单时由用户主动同步接口调用已认证的渠道查询流程。`submit.php` 返回的表单动作会由前端白名单解析后重建提交，不直接执行渠道原始 HTML。

参考资料：

- [易支付官方平台开发文档](https://www.8-pay.cn/doc)：页面跳转、`mapi.php` API、`payurl`、查询和退款字段。
- [易支付 YPay 开发文档](https://www.ezfpy.cn/doc)：`submit.php` 页面跳转参数和 MD5 签名说明。

## 4. 支付宝官方协议

### 4.1 推荐接入方式

支付宝官方接入应使用支付宝开放平台的应用配置、RSA2 签名和官方 SDK 或官方 OpenAPI，不应复用易支付的 `pid/key/type/money` 格式。当前 Adapter 通过渠道配置的 `product` 选择 `PAGE`、`WAP` 或 `PRECREATE`，不再读取通用 `scene` 组装官方请求。

项目是服务端生成支付动作、浏览器继续支付的形态，建议优先支持：

| 业务形态 | 官方接口 | 服务端结果 |
| --- | --- | --- |
| 电脑网站支付 | `alipay.trade.page.pay` | 生成支付宝 HTML 表单或支付页面动作 |
| 手机网站支付 | `alipay.trade.wap.pay` | 生成手机网站支付页面动作 |
| 扫码或当面付扩展 | `alipay.trade.precreate` | 获得二维码内容 |

电脑网站和手机网站是支付宝官方的产品接口，不应再用一个通用 `scene` 去拼装易支付字段。具体使用哪种支付宝产品，应由支付宝渠道配置和部署端能力决定。

### 4.2 订单查询、关闭和通知

支付宝官方订单生命周期至少需要覆盖：

- `alipay.trade.query`：服务端查询交易状态；
- `alipay.trade.close`：关闭未支付交易；
- `alipay.trade.refund`：后续退款能力；
- 支付宝异步通知：验签后读取交易状态、商户订单号、支付宝交易号和实收金额。

同步跳转只用于用户体验和页面展示，不能作为 Lumina 入账依据。支付成功必须以验签通过的异步通知或服务端可信查询为准。

### 4.3 配置要求

支付宝官方渠道需要独立配置：

- `appId`；
- 应用私钥；
- 支付宝公钥或公钥证书；
- 网关地址；
- 签名类型和字符集；
- 异步通知地址、同步跳转地址；
- 必要时的支付宝公钥证书链和应用公钥证书。

敏感私钥必须加密存储，只向管理员返回脱敏配置状态。Adapter 应负责组装官方公共参数、签名、生成页面表单、验签和解析官方响应。

当前实现还会校验 `alipay.trade.query`、`alipay.trade.precreate` 等 OpenAPI 响应的 RSA2 签名；查单和关单均通过同一官方网关调用。

参考资料：

- [支付宝开放平台网页/移动应用](https://open.alipay.com/module/webApp)：应用创建、开发配置和网页/移动应用接入入口。
- [支付宝官方 EasySDK](https://github.com/alipay/alipay-easysdk)：官方 SDK 的支付能力、电脑网站支付、手机网站支付、查询、关闭和退款 API 说明。
- [支付宝 API 列表](https://developer.alibaba.com/docs/api_list.htm?docType=4)：官方接口名称和能力索引。

## 5. 微信支付官方 API v3

### 5.1 推荐接入方式

微信支付官方 API v3 是 JSON REST 接口，不能沿用易支付或支付宝的参数格式。服务端请求需要使用商户私钥生成 `WECHATPAY2-SHA256-RSA2048` Authorization，带上商户号、商户证书序列号和请求签名。当前 Adapter 通过渠道配置的 `product` 选择 `JSAPI`、`H5`、`NATIVE` 或 `APP`。

普通商户常见下单接口如下：

| 微信产品 | 官方接口 | 典型返回 |
| --- | --- | --- |
| JSAPI/小程序 | `POST /v3/pay/transactions/jsapi` | `prepay_id`，再由客户端调起支付 |
| 微信外 H5 | `POST /v3/pay/transactions/h5` | `h5_url` |
| Native | `POST /v3/pay/transactions/native` | `code_url` |
| APP | `POST /v3/pay/transactions/app` | `prepay_id`，用于客户端 SDK 调起 |

这些是微信自己的产品接口。它们可以在 Adapter 内按部署环境分别实现，但不应被压缩成一个由 Lumina 统一拼接的 `scene` 请求。

### 5.2 回调、验签和解密

微信支付成功通知通过 POST 发送到下单时传入的 `notify_url`。回调请求头包含微信支付签名信息，商户必须验签；通知 body 中的交易资源使用 APIv3 密钥通过 AEAD_AES_256_GCM 解密后，才能读取商户订单号、微信支付订单号、交易状态和金额。

微信官方文档还明确建议：不能只依赖回调，商户应结合查询接口处理回调丢失或延迟；重复通知必须可安全重入。

### 5.3 配置要求

微信官方渠道需要独立配置：

- `appid`；
- `mchid`；
- 商户 API 证书序列号；
- 商户 API 私钥；
- APIv3 密钥；
- 微信支付公钥或平台证书；
- API 地址和通知地址；
- 根据产品需要的用户 `openid`、H5 场景信息或客户端能力。

微信支付官方文档推荐使用官方工具库封装 JSON、密钥加载、请求签名、请求头构建和响应验签。当前项目是 Node.js，若没有适用的官方 Node.js 工具库，应严格按 API v3 官方协议实现这些步骤，并为签名、验签、回调解密单独建立测试，不应退回到旧版 MD5/XML 或易支付格式。

当前实现要求配置微信支付公钥，并对 API 响应签名缺失或无效直接失败，不再静默跳过响应验签；H5、JSAPI、Native、APP 的产品路径和返回动作均在微信 Adapter 内完成。

参考资料：

- [微信支付 API v3 概述](https://pay.wechatpay.cn/doc/v3/merchant/4012081606)：API v3 的 JSON、RSA 签名、验签和回调加密规则。
- [微信 JSAPI/小程序下单](https://pay.wechatpay.cn/doc/v3/merchant/4012791897)：`/v3/pay/transactions/jsapi` 和 `prepay_id`。
- [微信 H5 下单](https://pay.wechatpay.cn/doc/v3/merchant/4012525153)：`/v3/pay/transactions/h5` 和 `h5_url`。
- [微信 Native 下单](https://pay.wechatpay.cn/doc/v3/merchant/4012791877)：`/v3/pay/transactions/native` 和 `code_url`。
- [微信 API v3 签名验签](https://pay.wechatpay.cn/doc/v3/merchant/4012365342)：请求、响应和回调签名规则。
- [微信支付成功回调通知](https://pay.wechatpay.cn/doc/v3/merchant/4012791861)：回调验签和 AES-256-GCM 解密。

## 6. Lumina 建议的内部边界

### 6.1 用户接口

用户创建充值订单时只提交：

- 人民币金额；
- 用户选择的支付方式或渠道实例；
- 必要的渠道身份信息，例如微信 JSAPI 所需的 `openid`。

用户接口不提交跨渠道 `scene`。如果以后需要让用户选择“电脑网站、手机网站、扫码”等产品形态，应由具体官方渠道定义专属选项，或由后端根据请求来源和渠道配置决定。

当前充值接口只接收金额、支付方式和必要的 `payerOpenId`；`PaymentOrder.scene` 仍返回给旧客户端，但它是兼容快照，不参与新的渠道请求。

### 6.2 Adapter 职责

每个 Adapter 独立负责：

- 渠道配置校验；
- 官方或易支付专属下单请求；
- 渠道签名和请求认证；
- 响应验签和错误解析；
- 支付动作生成；
- 异步通知验签、解密和字段映射；
- 主动查单、关单和退款能力。

支付宝和微信的产品路径、易支付的 endpoint/查询方式等协议专属配置也由各自 Adapter 解释，统一服务层不再传递通用场景。

PaymentService 只负责：

- 创建和复用 Lumina `PaymentOrder`；
- 订单金额、币种、渠道实例和状态校验；
- 回调幂等；
- 通过 `WalletService` 入账；
- 不同渠道结果映射为统一内部状态。

### 6.3 统一结果而非统一请求

可以继续保留统一的结果动作：

- 跳转 URL；
- 受限 HTML 表单；
- 二维码内容；
- JSAPI 调起参数。

但这些只是前端执行支付所需的结果类型，不能反向要求所有渠道都接受 `WEB/H5/QR/JSAPI` 这组统一请求场景。

## 8. 当前阶段的明确限制

- 本次实现没有改变数据库结构；`PaymentOrder.scene` 作为历史兼容字段保留。
- 当前没有确认实际使用的易支付服务商是哪一家；在实现前必须以该服务商后台文档和实际响应为准。
- 支付宝和微信官方接口需要真实商户配置、证书/密钥和沙箱或生产联调环境，单靠本地单元测试不能证明真实支付链路可用。
- 外部渠道请求一旦发出，结果不确定时不能自动切换渠道或创建第二笔业务订单。
- 本地工作区没有可用的支付测试环境；本次提交后应在 `lch:/root/lumina` 拉取代码，执行后端构建/测试和项目已有 E2E 检查。真实支付闭环仍需对应服务商的沙箱或生产回调地址。
