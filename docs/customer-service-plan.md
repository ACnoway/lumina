# 客服功能规划

## 1. 项目现状

- 前端使用 Next.js，已有用户聊天页和管理后台。
- 后端使用 NestJS + Prisma + PostgreSQL + Redis。
- 已有 JWT、`ADMIN/SUPER_ADMIN` 权限、审计日志和 SSE 流式聊天能力。
- Nginx 已关闭代理缓冲并配置了较长的读取超时，具备承载 SSE 的基础。
- 客服功能应作为独立业务域实现，不复用 AI 聊天会话，避免混入模型、计费和 AI 消息逻辑。

## 2. 用户端功能

新增独立客服入口和客服页面：

- 首页、顶部导航或个人中心增加“联系客服”入口。
- 用户默认拥有一个进行中的客服会话。
- 提供类即时聊天交互：
  - 消息列表
  - 输入框和发送状态
  - 历史消息加载
  - 客服回复实时到达
  - 断线重连后自动补齐消息
- 展示会话状态：等待客服、等待用户、已结束。
- 第一阶段只支持纯文本消息，不加入图片、文件和语音。

## 3. 管理端功能

在现有 `/admin` 增加“客服”页签：

- 左侧显示客服会话列表：
  - 客户昵称
  - 邮箱或脱敏手机号
  - 最近一条消息
  - 最后消息时间
  - 未读数量
  - 会话状态
- 新客户消息置顶并高亮。
- 客服页签或后台顶部显示未读总数。
- 右侧展示完整聊天记录。
- 管理员可以回复客户、标记已读、结束会话和重新打开会话。
- 第一阶段采用所有管理员共享一个客服队列，不做客服人员分配和抢单。

## 4. 后端数据模型

新增独立客服领域，预计包含：

### SupportConversation

- 用户 ID
- 会话状态
- 最后一条消息摘要
- 最后消息时间
- 用户未读数
- 管理端未读数
- 创建时间和更新时间

### SupportMessage

- 会话 ID
- 发送者类型：用户、管理员、系统
- 发送者用户 ID
- 消息内容
- 创建时间

增加用户、消息时间、状态和未读相关索引。

不修改现有 `ChatSession`、`ChatMessage`，避免影响 AI 聊天和计费链路。

## 5. API 规划

### 用户端

- 创建或获取当前客服会话
- 查询客服会话
- 分页查询消息
- 发送客服消息
- 标记用户侧已读
- 订阅客服消息实时事件

### 管理端

- 分页查询客服会话列表
- 按状态、未读和关键词筛选
- 查询指定会话消息
- 发送管理员回复
- 修改会话状态
- 标记管理端已读
- 订阅新客户消息事件
- 查询未读总数

所有接口继续复用现有 JWT 和管理员 RBAC。

## 6. 即时交互方案

推荐采用：

- 客户端发送消息使用普通 `POST`。
- 服务端通过 SSE 推送新消息。
- Redis 用于多进程或多容器之间转发客服消息事件。
- 前端使用基于 `fetch` 的 SSE 流读取，以便携带现有 Bearer Token。
- 断线后通过最后消息 ID 或时间戳补偿，避免消息丢失。
- 增加心跳、自动重连、`Cache-Control: no-cache` 等处理；SSE 建连超过 35 秒未完成时进入轮询兜底，并以 5 秒间隔自动补偿消息，避免代理返回 524 后只能手动刷新。
- Nginx 对用户端和管理端 SSE 使用独立直通规则，关闭代理缓存/缓冲并设置 600 秒读写超时；若外层 Cloudflare 仍限制长连接，前端自动轮询仍能保持消息可见。

这样可以复用当前项目已有的 SSE 和 Redis 基础，不必立即引入 WebSocket。

## 7. 安全与业务规则

- 用户只能查看自己的客服会话。
- 普通用户不能访问管理端客服队列。
- 停用用户不能继续发送消息。
- 限制消息长度和发送频率。
- 消息按纯文本处理，避免 HTML/XSS。
- 管理员回复和状态变更写入审计日志，但不把完整消息内容写入审计详情。
- 客服消息不计入光子余额，也不走 AI Provider。

## 10. 第一阶段不包含

- AI 自动客服或人工转 AI。
- 图片、文件和语音附件。
- 多客服分配、抢单和排班。
- 邮件、短信或浏览器 Push 通知。
- 客服 SLA、评价和工单统计报表。
