# 充值订单流程改造大纲

> 实施状态（2026-10-02）：本大纲所述的充值订单跳转支付、待支付订单展示与原订单恢复已完成代码改造；**远程环境验证尚未执行，不能视为已验收**。
>
> 验证将遵循“本地提交并推送 → SSH `lch` → 在 `/root/lumina` 拉取 → 使用 pnpm 8.15.0 测试”的顺序。真实支付宝、微信或易支付交易仍需要相应沙箱或商户凭据联调。

## 1. 改造目标

整体参考 WHMCS 创建订单的体验，调整 Lumina 当前充值流程：

- 用户确认支付方式、充值金额、当前余额和预计到账结果。
- 点击创建订单后，创建一笔未支付的充值订单。
- 支付渠道页面在新标签页打开。
- 个人中心的账单中展示未支付充值订单，并提供“去支付”按钮。
- 个人中心提示用户存在未支付订单。
- 支付成功后再增加余额，并从未支付订单列表中移除。

以下内容保留原始设计依据，并同步记录本次实现的边界与验证要求。

## 2. 改造前项目现状

项目是 pnpm monorepo：

- `apps/backend`：NestJS、Prisma、PostgreSQL、Redis。
- `apps/frontend`：Next.js、React、Tailwind CSS。
- `packages/shared`：前后端共享 DTO 和类型。

当前已经具备：

- `PaymentOrder` 支付订单模型。
- `PaymentChannel` 支付渠道配置模型。
- 易支付、支付宝、微信支付适配器。
- 异步支付通知和服务端主动查单。
- 支付成功后的钱包充值及幂等处理。
- 个人中心充值页面和钱包流水账单。

改造前的主要缺口：

- 后端充值场景固定为二维码 `QR`。
- 支付宝或其他跳转动作可能在当前页跳转，或由前端临时创建弹窗。
- 账单目前只查询 `WalletTransaction`，未支付的 `PaymentOrder` 不会展示。
- 个人中心没有统一的未支付订单提示和订单恢复支付入口。

## 3. 订单与钱包流水的职责边界

继续复用已有 `PaymentOrder`，不新增一套充值订单表。

### PaymentOrder

表示外部支付系统中的充值订单，负责保存：

- Lumina 订单号。
- 用户、支付渠道和支付方式。
- 人民币金额和光子到账金额。
- 创建时的充值汇率快照。
- `CREATED`、`PENDING`、`SUCCEEDED`、`FAILED`、`CLOSED`、`EXPIRED` 等状态。
- 支付动作、支付平台订单号和过期时间。

### WalletTransaction

表示 Lumina 内部钱包余额变化，只在支付成功后生成 `RECHARGE` 流水。

未支付订单不能提前生成充值流水，也不能提前增加余额。

账单页面可以同时展示两种数据，但不能把未支付订单伪装成钱包流水。

## 4. 后端实现

### 4.1 调整支付场景

取消充值流程中固定使用 `PaymentScene.QR` 的逻辑。

按支付方式选择支持跳转的场景：

- 支付宝优先使用 `WEB`。
- 微信优先使用 `H5`。
- 只选择能够返回跳转地址或 HTML 表单的渠道。
- 如果首选场景不可用，可选择同一支付方式支持的其他非二维码跳转场景；如果仍没有可用渠道，明确返回“当前支付方式暂不可用”。

不在没有用户确认的情况下静默降级为二维码支付。

微信 H5 仅在受信任反向代理部署中读取转发的客户端 IP；Docker 生产编排通过 `TRUST_PROXY=true` 启用该行为。

### 4.2 未支付订单查询

当前用户通过以下接口查询订单：

```text
GET /payments/orders
```

默认返回 `CREATED/PENDING` 订单；可通过 `status=CREATED|PENDING`、时间排序和分页参数缩小结果范围。

接口需要满足：

- 只返回当前用户自己的订单。
- 默认排除已成功、失败、关闭和过期订单。
- 支持按状态和时间排序。
- 返回订单金额、预计到账光子、支付方式、渠道、创建时间、过期时间和订单号。
- 订单动作只返回给订单所属用户。

如果查询过程中发现订单已超过 `expireAt`，应同步将其标记为 `EXPIRED`，避免继续展示“去支付”。

### 4.3 复用原订单继续支付

账单中的“去支付”使用 `POST /payments/orders/:orderNo/pay` 恢复原有 `PaymentOrder`，不能重新创建第二笔订单。

规则：

- 仅允许 `CREATED/PENDING` 且未过期的订单继续支付。
- 复用原订单号和原订单金额。
- 不改变订单的光子金额和汇率快照。
- 不产生新的 `PaymentOrder`。
- 支付成功仍统一进入现有 `processPaymentSuccess` 流程。

如果已保存的支付动作失效，恢复支付接口可为同一订单重新生成支付动作；仍必须绑定原订单，不得重新创建业务订单。

### 4.4 保持支付入账安全规则

以下规则保持不变：

- 创建订单不调用 `WalletService.recharge()`。
- 只有验签成功的异步通知，或服务端明确确认成功的查单，才允许入账。
- 回调金额和币种必须与本地订单一致。
- 已关闭、失败或过期的订单不能恢复入账。
- 重复通知只能产生一条钱包充值流水。
- 前端跳转、支付返回页和前端轮询不能直接触发余额增加。

## 5. 前端实现

主要修改个人中心充值与账单区域。

### 5.1 充值确认信息

充值区域增加确认摘要：

- 当前光子余额。
- 本次充值金额。
- 当前支付方式。
- 预计到账光子。
- 充值后预计余额。
- 订单过期时间或支付有效期提示。

用户确认这些信息后，再点击“创建充值订单”。

### 5.2 新标签页打开支付

创建订单时：

1. 在用户点击事件同步打开空白新标签页，避免浏览器拦截。
2. 调用后端创建订单接口。
3. 如果返回 `REDIRECT_URL`，将新标签页跳转到支付地址。
4. 如果返回 `HTML_FORM`，在新标签页提交支付表单。
5. 当前个人中心页面继续保留，用于查看订单状态和账单。
6. 创建失败时关闭空白标签页，并在原页面显示错误。

当前页面不能再使用 `window.location.assign()` 覆盖个人中心页面。

### 5.3 账单展示未支付订单

账单页顶部增加“待支付充值订单”区域，订单卡片展示：

- 状态：待支付。
- 充值金额。
- 预计到账光子。
- 支付方式和渠道。
- 创建时间。
- 过期时间。
- Lumina 订单号。
- “去支付”按钮。

已支付订单继续通过 `WalletTransaction` 展示实际余额变化，避免同一笔充值重复展示为两笔入账记录。

### 5.4 个人中心提示

在个人中心概览页和账单页增加未支付提示：

- 显示未支付订单数量。
- 显示待支付总金额或最近一笔订单信息。
- 提供跳转到账单或直接“去支付”的入口。
- 支付成功后自动刷新提示状态、余额和账单列表。

## 6. 订单状态流转

```text
创建充值订单
    │
    ▼
CREATED
    │ 渠道下单成功
    ▼
PENDING ─────────────┐
    │                 │
    │ 支付成功回调     │ 过期/失败/关闭
    ▼                 ▼
SUCCEEDED       EXPIRED / FAILED / CLOSED
    │
    ▼
WalletTransaction(RECHARGE)
    │
    ▼
钱包余额增加
```

其中：

- `CREATED/PENDING` 显示“去支付”。
- `SUCCEEDED` 显示支付成功，不再显示“去支付”。
- `EXPIRED/FAILED/CLOSED` 显示终态说明，不允许继续支付。
